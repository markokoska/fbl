## 3 Дизајн на апликацијата

### 3.1 Архитектура на системот

Апликацијата следи класична three-tier архитектура: презентациски слој (React SPA), апликациски слој (ASP.NET Core REST API + SignalR хабови) и слој за податоци (PostgreSQL). Сите три слоеви се пакувани во еден Docker контејнер кој се поставува на Render.

[ОВДЕ СЛИКА: Слика 1. Високо-нивен преглед на архитектурата — клиент (browser) → React SPA сервиран од .NET → ASP.NET Core API + SignalR Hub → PostgreSQL]

Комуникацијата меѓу клиентот и серверот се одвива на два канала:

- **REST API** (синхрон, request/response) за стандардни CRUD операции, најава, регистрација, читање на тимови и состојби,
- **SignalR WebSocket** (асинхрон, server-push) за real-time настани — пиковите во драфт собата и ажурирањата на ранг-листата за време на live гејмвик.

### 3.2 Модел на податоци (ER дијаграм)

[ОВДЕ СЛИКА: Слика 2. ER дијаграм со клучните ентитети — AppUser, FantasyTeam, FantasyPick, BundesligaPlayer, Gameweek, League, LeagueMember, DraftPick, WaiverClaim, DroppedPlayer, MatchEvent]

Главните врски во моделот се:

- **AppUser → FantasyTeam** (1:N) — еден корисник може да има повеќе тимови (по еден за глобалниот режим и по еден за секоја лига во која членува). Уникатноста е загарантирана преку композитен индекс `(UserId, LeagueId)`.
- **FantasyTeam → League** (N:1, опционално) — `LeagueId` е nullable; ако е `NULL`, тимот е глобален.
- **FantasyTeam → FantasyPick** (1:N) — секој тим има по 15 пика за секоја гејмвик. Squad position 1-11 се старачки, 12-15 се клупа.
- **League → DraftPick** (1:N) — за драфт лиги. Уникатниот индекс `(LeagueId, PlayerId)` ја загарантира уникатноста на сопственоста — еден играч може да биде драфтиран од само еден менаџер во дадена лига.
- **DroppedPlayer** — записи за играчи отпуштени во тековната гејмвик; тие остануваат заклучени до следната гејмвик и не можат да бидат поседувани повторно.

### 3.3 Типови корисници и улоги

Системот разликува две улоги, стандардно конфигурирани преку ASP.NET Core Identity:

- **Player** — стандарден корисник. Може да најава, да креира тимови, да се приклучи во лиги, да прави трансфери, да драфтира и да поднесува вејвер барања.
- **Admin** — има пристап до администраторски панел за управување со гејмвици, симулирање на настани во натпревари, мануелно провоцирање обработка на вејвери, и преглед на сите тимови во системот.

Улогите се seedovани при стартување на апликацијата (во `Program.cs`), и се додаваат на корисниците преку `UserManager<AppUser>.AddToRoleAsync()`. Заштитата на ендпоинтите се остварува преку атрибутот `[Authorize(Roles = "Admin")]`.

### 3.4 Три режими на игра

Една од централните технички одлуки на проектот е поддршка на **три режими на игра** во ист систем:

#### Глобален режим
Секој корисник има еден тим (со `LeagueId = NULL`) кој се натпреварува на единствена глобална ранг-листа. Сите корисници меѓу себе. Нема приватни лиги, нема драфт. Едноставен, низок-фрикционен влез за нови играчи.

#### Класична лига (Classic League)
Корисниците создаваат или се приклучуваат на приватна лига преку join код. **За секоја лига во која членуваат, корисниците прават засебен тим.** Тоа значи дека истиот корисник може да има 5 различни тимови ако членува во 5 класични лиги — секој со свои избрани играчи, капитен, трансфери и поени.

Технички, тоа е реализирано преку nullable `FantasyTeam.LeagueId` колоната — глобалниот тим има `LeagueId = NULL`, а лигашките тимови имаат соодветна вредност. Композитниот уникатен индекс `(UserId, LeagueId)` загарантира дека корисникот не може да има два тима за иста лига.

#### Драфт лига (Draft League)
Создавачот на лигата го дефинира максималниот број менаџери (по дифолт 8). Откако сите членови ќе се приклучат, создавачот стартува **жив snake-драфт**. Секој играч во Бундеслигата може да биде поседуван од **само еден менаџер во таа лига** — сопственоста е загарантирана преку уникатен индекс `(LeagueId, PlayerId)` на `DraftPicks` табелата.

По завршувањето на драфтот, тимовите автоматски се создаваат во `FantasyTeams` табелата со драфтираните играчи. Менаџирањето во наредните гејмвици се одвива преку **вејвер систем** наместо стандардни трансфери. Чиповите (Wildcard, Bench Boost итн.) и капитен/вицекапитен **не се применливи** во драфт режим — секој пик е заземен од снејк-редоследот, а сите играчи имаат еднаков мултипликатор.

## 4 Имплементација и алгоритми

Овој дел опишува неколку алгоритамски компоненти кои претставуваат суштинскиот придонес на апликацијата над еден стандарден CRUD систем.

### 4.1 Систем за поени (FPL scoring)

Поените се пресметуваат на ниво на индивидуален играч за дадена гејмвик, врз основа на настани во `MatchEvent` табелата. Правилата следат стандардниот FPL модел:

| Настан | Поени |
|---|---|
| Минути одиграни (1-59 мин) | +1 |
| Минути одиграни (60+ мин) | +2 |
| Гол (напаѓач) | +4 |
| Гол (полузаштитник) | +5 |
| Гол (одбранбен) | +6 |
| Гол (голман) | +6 |
| Асистенција | +3 |
| Чисти мрежи (одбрана/голман, 60+ мин) | +4 |
| Чисти мрежи (полузаштитник, 60+ мин) | +1 |
| Жолт картон | -1 |
| Црвен картон | -3 |
| Автогол | -2 |
| Промашен пенал | -2 |
| Одбранет пенал (голман) | +5 |
| Бонус поени | +1 / +2 / +3 |

Поените се акумулираат по играч и потоа се множат со мултипликатор (1× за обичен играч, 2× за капитен, 3× за капитен под Triple Captain чип).

### 4.2 Алгоритам за автоматски замени (auto-substitutions)

Кога старачки играч не настапи во дадена гејмвик (нема „Минути одиграни" настан), системот **автоматски** го заменува со еден од клупата според следните правила:

1. **Голманот (GK)** има посебен слот — старачкиот голман може да биде заменет само од клупскиот голман, и обратно.
2. **Полевните играчи** (DEF/MID/FWD) се заменуваат во редослед на клупата (12 → 13 → 14 → 15), при што секоја замена мора да резултира со **валидна формација**: ≥3 одбранбени, ≥2 полузаштитници, ≥1 напаѓач.
3. **Клупски играч кој исто така не настапил не може да дојде како замена.**

Алгоритмот е имплементиран во методата `LeaderboardService.ComputeAutoSubs`, со скратен прикажан C# код:

```csharp
public static (HashSet<int> effectivePlayingIds, List<(int outId, int inId)> subs)
    ComputeAutoSubs(List<FantasyPick> picks, HashSet<int> playedIds)
{
    var starters = picks.Where(p => p.SquadPosition <= 11).ToList();
    var bench = picks.Where(p => p.SquadPosition >= 12)
                     .OrderBy(p => p.SquadPosition).ToList();
    var subs = new List<(int, int)>();
    var effective = new List<FantasyPick>(starters);

    // 1. GK замена (посебен слот)
    var startGk = starters.FirstOrDefault(p => p.Player.Position == PlayerPosition.GK);
    var benchGk = bench.FirstOrDefault(p => p.Player.Position == PlayerPosition.GK);
    if (startGk != null && !playedIds.Contains(startGk.PlayerId)
        && benchGk != null && playedIds.Contains(benchGk.PlayerId))
    {
        effective.Remove(startGk);
        effective.Add(benchGk);
        subs.Add((startGk.PlayerId, benchGk.PlayerId));
    }

    // 2. Полевни замени со валидација на формација
    var dnpOutfield = starters
        .Where(p => p.Player.Position != PlayerPosition.GK
                 && !playedIds.Contains(p.PlayerId))
        .OrderBy(p => p.SquadPosition).ToList();

    foreach (var dnp in dnpOutfield)
    {
        foreach (var cand in bench.Where(p => p.Player.Position != PlayerPosition.GK
                                           && playedIds.Contains(p.PlayerId)))
        {
            var trial = effective.Where(p => p.Id != dnp.Id).ToList();
            trial.Add(cand);
            int defs = trial.Count(p => p.Player.Position == PlayerPosition.DEF);
            int mids = trial.Count(p => p.Player.Position == PlayerPosition.MID);
            int fwds = trial.Count(p => p.Player.Position == PlayerPosition.FWD);

            if (defs >= 3 && mids >= 2 && fwds >= 1)
            {
                effective = trial;
                subs.Add((dnp.PlayerId, cand.PlayerId));
                break;
            }
        }
    }

    return (effective.Select(p => p.PlayerId).ToHashSet(), subs);
}
```

Дополнително, при пресметката на поените за капитенот се применува **DNP fallback**: ако капитенот не настапил, мултипликаторот ×2 се пренесува на вицекапитенот (под услов и тој да настапил).

### 4.3 Snake-драфт алгоритам

Snake-драфтот е метод за распределување на играчи во кој редоследот на пиковите ротира. Во рунда 1, пиковите се вршат во редослед 1 → 2 → ... → N. Во рунда 2, **обратно**: N → N-1 → ... → 1. Во рунда 3 повторно нормално, итн.

Овој дизајн обезбедува правичност — менаџерот кој пикира последен во рунда 1 ќе пикира прв во рунда 2, со што се компензира за тоа дека во рунда 1 ја имаше последната шанса за најатрактивните играчи.

Математички, ако `P` е глобалниот број на пикот (1-базиран) и `N` е бројот на менаџери, тогаш:

```
round = ((P - 1) / N) + 1                  // 1-базирана рунда
posInRound = ((P - 1) % N) + 1             // 1-базирана позиција во рундата
pickerIndex = (round нечетна)
              ? posInRound - 1
              : N - posInRound              // обратен редослед во парни рунди
```

Кодот во `DraftService.GetPickerIndex` е тривијална имплементација:

```csharp
public static int GetPickerIndex(int pickNumber, int memberCount)
{
    int round = ((pickNumber - 1) / memberCount) + 1;
    int posInRound = ((pickNumber - 1) % memberCount) + 1;
    return (round % 2 == 1) ? posInRound - 1 : memberCount - posInRound;
}
```

Член-листата е сортирана по време на приклучување (`JoinedAt`) — првиот корисник што се приклучил го добива индексот 0.

При секој пик, серверот:

1. Валидира дека е ред на тој корисник (споредба со `GetPickerIndex(currentPickNumber, members.Count)`).
2. Проверува дека играчот не е веќе драфтиран во таа лига (преку уникатниот индекс — на ниво на база).
3. Проверува дека позиционата квота не е надмината (≤2 GK, ≤5 DEF, ≤5 MID, ≤3 FWD).
4. Запишува нов `DraftPick` ред.
5. Го инкрементира `CurrentPickNumber` и поставува нов `CurrentPickDeadline = now + DraftPickSeconds`.
6. Ако ова бил последниот пик (15 × N), ја стартува **финализацијата** — креира `FantasyTeam` редови за секој менаџер со драфтираните играчи во default 1-4-4-2 формација.
7. Емитува `PickMade` настан преку SignalR кон сите клиенти во драфт собата.

**Автоматски пик (auto-pick)** при истек на тајмерот е имплементиран во `DraftAutoPickService` background сервисот. Кога `CurrentPickDeadline < now`, серверот:

1. Идентификува кого е ред преку snake-формулата.
2. Пресметува кои позиции тој менаџер сè уште ги треба (на пр. ако веќе има 2 GK, GK не е потребна).
3. Бира **највисоко рангиран расположлив играч** (по `TotalPoints`) на потребна позиција.
4. Изведува пик во негово име, означен со `WasAutoPick = true`.

### 4.4 Вејвер опашка и слободни агенти

По завршувањето на драфтот, менаџирањето на тимот не може да се прави преку стандардни трансфери (бидејќи играчите се поседувани од конкретни менаџери). Наместо тоа, секоја гејмвик постои **вејвер прозорец** со следниот животен циклус:

1. **Фаза 1 — Опашка (Queue)**: за време на тековната гејмвик, секој менаџер може да поднесе **подредена листа** од вејвер барања — „размени играч A за играч B", „размени C за D", итн., со приоритет 1, 2, 3...
2. **Фаза 2 — Обработка (Processing)**: 24 часа пред дедлајнот на следната гејмвик, серверот автоматски ги обработува барањата:
   - Менаџерите се сортираат во **обратен редослед на пласманот** (последниот по поени иде прв),
   - За секој менаџер, неговите барања се обработуваат во редослед на приоритет,
   - Барањето успева ако таргет играчот **сè уште не е поседуван** во лигата,
   - Ако успее, размената се применува за следната гејмвик и таргет играчот веќе не е расположлив за подоцнежни барања.
3. **Фаза 3 — Слободна агенција (Free Agency)**: по обработката, до дедлајнот, сите играчи кои сè уште не се поседувани можат **директно** да се земат, прв-дојден-прв-послужен, без опашка.
4. **Фаза 4 — Заклучено (Locked)**: по дедлајнот, нема промени до следната гејмвик.

Алгоритмот за обработка на опашката е имплементиран во `WaiverService.ProcessLeagueWaivers`. Главните чекори се:

```csharp
// Сортирај тимови по обратен редослед на пласман
var teams = await _db.FantasyTeams
    .Where(t => t.LeagueId == leagueId)
    .OrderBy(t => t.TotalPoints + t.GameweekPoints)
    .ToListAsync();

foreach (var team in teams)
{
    var myClaims = pendingClaims
        .Where(c => c.UserId == team.UserId)
        .OrderBy(c => c.Priority);

    foreach (var claim in myClaims)
    {
        // 1. PlayerOut мора сè уште да биде во тимот
        // 2. PlayerIn мора да не е поседуван од никого во лигата
        // 3. PlayerIn мора да не е заклучен (отпуштен оваа гејмвик)
        if (validClaim) {
            ApplySwap(team, claim);
            RecordDrop(claim.PlayerOutId);  // следно — заклучи го
            claim.Status = WaiverClaimStatus.Succeeded;
        } else {
            claim.Status = WaiverClaimStatus.Failed;
        }
    }
}
```

### 4.5 Заклучување на отпуштени играчи

Една нетривијална game-design одлука е спречување на „cycling" (прво те пуштам играчот, па потоа го земам назад). Без ова, корисниците би можеле да:

- го отпуштат „зезнатиот" играч за да ослободат место и подоцна да го вратат;
- стратешки да блокираат противнички намери преку привремени отпуштања.

Решението е воведување `DroppedPlayer` ентитет:

```csharp
public class DroppedPlayer
{
    public int Id { get; set; }
    public int LeagueId { get; set; }
    public int PlayerId { get; set; }
    public int GameweekId { get; set; }     // гејмвик за која важи lock-от
    public string DroppedByUserId { get; set; }
    public DateTime DroppedAt { get; set; }
}
```

При секое успешно вејвер барање ИЛИ директна слободно-агенциска размена, серверот запишува `DroppedPlayer` ред со тековната гејмвик. Кога се листаат расположливите играчи, оние кои се отпуштени се **прикажуваат** во списокот, но со икона за заклучен и без копче за земање.

Кога новата гејмвик ќе стане „upcoming" (т.е. кога претходната ќе почне или ќе заврши), претходните `DroppedPlayer` редови повеќе не важат — филтрирањето е по `GameweekId == upcomingGw.Id`, така lock-от природно се крева.
